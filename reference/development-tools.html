Development tools ​

GoMeta's output is a set of evaluated values at the Components of a file, not a file: as GoMeta's creator puts it, "the output of GoMeta is not readily directly observable. For that reason, a couple of tools and colorful printouts can serve to track and illustrate the internal process of the package". This page is the reference for those tools at release 0.4.1 (alpha): the print tools, which show what a run produced, and the basic renderer, which writes a rendered copy of the file. They are not part of a GoMeta run: the GoMeta Engine uses none of them, a run gives the same delivery without them, and they change nothing in it. They read the delivery through the same public surface an Extension uses — the Public API. Their purpose: the print of the evaluated values shows what has been evaluated for which Component, and the print of the BLS Component tree lets anyone see and check how BLS parsed the file.

1. The print tools ​

From a shell, at the repository's root and after Pkg.instantiate() in its tests project, one call prints one view of one file:

julia --startup-file=no --project=tests devtools/devtools.jl <verb> <file>
verbprints
evals-treethe full delivery view: every Block and Line of the BLS Component tree, each with the evaluated values recorded at it and every value's handle decoded; a Line that ends in a metaSegment — a #~ with or without a statement after it — carries its values with that Segment named; a Component without a value of its own is marked so
bls-treethe Component-tree view: every Component with its settribute and its named integers
treethe BLS Component tree printed one row per input line: each Component's flavor and content, Blocks, Lines and Segments nested
segmentsthe same rows with the input's line numbers in front
evalsthe evaluated values alone, one row per value
tracethe evaluated values with each row's decoded Component's handle
renderthe rendered copy of the file — the basic renderer's output (section 2)
comparisonone line per Component and, for every Block, Line and Segment, one line per Alterant with its evaluated value and its source, sorted — a text form by which the deliveries of two versions or variants of GoMeta for one input are compared by their values

The delivery views and the Component-tree view from Julia:

julia
using GoMeta
include(joinpath(pkgdir(GoMeta), "devtools", "devtools.jl"))
delivery = GoMeta.goMeta(read("some.jl"))

print_altValues_evals(delivery)                                            # the compact delivery view
print_altValues_evals(delivery; include_empty = true, show_handles = true)   # the full delivery view
print_BLS_Component_Tree(delivery)                                         # the Component-tree view
write_altValues_evals_to_file("evals.html", delivery; include_empty = true)  # the same views as files (.html or .txt)
write_BLS_Component_Tree_to_file("tree.html", delivery)

The compact delivery view leaves out the Components that carry no value of their own and the handles. The full delivery view is the one to read first — it says what the Engine evaluated for which Component. The Getting started page and the Syntax & semantics page embed it for the two example files; the two other views of the first example file follow here.

The tools carry their own check, a battery under devtools/probes/ that fails loudly when the surface they read has changed.

2. The basic renderer: a proxy to check by eye ​

The basic renderer writes a rendered copy of the file in which each piece appears as its evaluated Visib value says — shown, hidden or discarded. For GoMeta's creator it is simply a proxy to check what GoMeta has evaluated: what matters is what GoMeta evaluates, not what its proxy shows. Strictly speaking it is no Extension: it lives under the package's development tools, and it is there because it serves a vital purpose for the package's development. It behaves like one, though: it reads the delivery through the public surface — the BLS Component tree through BLS's own functions, every Visib value through the Engine's answer function, evaluatedAltValue — and it evaluates nothing itself. It is loaded explicitly, at the top level:

julia
include(joinpath(pkgdir(GoMeta), "devtools", "load_basic_renderer.jl"))   # at the top level
out = Main.BasicRenderer.outputs(delivery)   # (blsStructure_bytes, render_bytes)
print(String(copy(out.render_bytes)))        # the rendered copy

It returns a pair: the tree print of section 1 (the tree verb) and the rendered copy. The tree print is the BLS Component tree as the parser built it and holds no evaluated values; the tools print it and the test suite pins it. No Extension takes this pair; an Extension works from the delivery. The package's test suite pins the pair byte for byte — the rendered copy against the committed reference files under the examples, the tree print against its committed copy: the renderer must produce consistent outputs.

3. What the rendered copy shows ​

Measured on the two example files, whose rendered copies the package commits under examples/OutFileFolder/ and the test suite pins (the second's is embedded in section 6):

  • A discarded Component leaves no bytes of its own.

  • A hidden Line is written behind the file format's hide marker — ## in Julia — and so is every non-empty line of a hidden Block that has no Visib value of its own — a line with its own value is written as that value says: the first example file's line 30, which ends in its own #~ show, is written as it is; a hidden empty line stays an empty line (the second example file's line 40).

  • A line that already begins with the marker is written as it is, never marked twice.

  • A hidden metaLine keeps its own marker: hide is visibility, so the metadata stays metadata in the rendered copy; a discarded metaLine is gone (the second example file's line 51).

  • An inline metaSegment is kept as it is on a shown line and, on a hidden one, written behind its own ## as the line is.

The two ## are two things: in the input ## opens a comment for the reader; in the rendered copy the input's comments keep their ##, and the tool writes ## before what it hides — its hide marker.

4. What the test suite pins ​

Over the committed examples the shipped tests assert that the same input and configuration give a byte-identical tree print and rendered copy in every run; that a discarded Component leaves no bytes and every non-empty line evaluated hidden carries the marker; that the tree print holds no evaluated values; and that the evaluated values are the same in every run.

5. Line endings ​

A file with CRLF line endings (a carriage return before each line feed) is read as if its endings were LF (a line feed alone), and the rendered copy comes out with LF endings; the bytes within a line are kept as they are (see the Public API page).

6. A worked example ​

In the second example file (examples/InFileFolder/file_for_Example_Extended.jl), line 14 is a text line that ends in #~ hide and line 15 a line that ends in #~ discard. In the rendered copy line 14 appears behind the hide marker, its trailing metaSegment marked with it, and line 15 is absent — as the file itself says, on its line 16: "Input line 15 will be missing from the output file!"
